# `.g3a` / Add-in 背景与技术路线

## 1. `.g3a` 是什么？

在 Casio fx-CG 系列图形计算器中，`.g3a` 是 Add-in 应用文件格式之一。它可以被复制到计算器的存储内存中，并在主菜单中以独立应用图标的形式出现。

它并不只用于游戏。理论上只要程序符合平台接口和资源限制，就可以做成：

- 游戏
- 工程工具
- 数学/统计工具
- 可视化程序
- 文件浏览器
- 解释器或运行环境

PythonExtra 本身就是一个典型例子：它不是普通 `.py` 文件，而是一个 `.g3a` Add-in；它运行后再为用户提供 MicroPython 环境。

## 2. 从 `.g1a` 到 `.g3a`

Casio 早期图形计算器平台已有 Add-in 生态，例如 fx-9860G 系列常见 `.g1a`。进入彩屏 Prizm / fx-CG 时代后，Add-in 文件体系演进为 `.g3a`。

可以把这条历史理解成：

```text
fx-9860G 等平台
    ↓
.g1a Add-in
    ↓
彩屏 Prizm / fx-CG 系列
    ↓
.g3a Add-in
```

二者不是简单“改后缀”，而是对应不同平台与文件结构，但设计思想具有延续性：**让用户在官方主菜单之外运行第三方原生应用。**

## 3. 三条典型路线

### 路线 A：安装现成 `.g3a`

```text
下载 .g3a
   ↓
复制到计算器存储根目录
   ↓
主菜单出现应用
   ↓
运行
```

GravityDuck 属于这种。

### 路线 B：PythonExtra + `.py`

```text
PythonExtra.g3a
   ↓
MicroPython
   ↓
your_script.py
   ↓
在计算器上解释执行
```

这条路线适合快速原型、教学、小型工具和小游戏。

### 路线 C：C + fxSDK/gint

```text
C 源码
  ↓
gint API
  ↓
sh-elf-gcc 交叉编译
  ↓
fxSDK 构建
  ↓
program.g3a
  ↓
fx-CG50 原生运行
```

这条路线更适合追求性能、复杂绘制、较高帧率和更完整的软件产品化。

## 4. 为什么 Python 版和原生 C 版性能不同？

PythonExtra 中的 `.py` 由 MicroPython 解释执行。很多操作需要经过解释器对象、函数调用和运行时处理。

原生 C 则被交叉编译成目标 CPU 的机器码，运行路径更短。

因此：

```text
Python 路线：
.py → MicroPython → gint/硬件

原生路线：
C → 机器码 → gint/硬件
```

这也是为什么同样的地图、碰撞和 Sprite 逻辑，在原生 C 中通常能承受更高的更新频率和更复杂的画面。

## 5. `.py` 能不能“转换成 `.g3a`”？

严格说，不能把 `.py` 直接改后缀或一键转换成高性能原生 `.g3a`。

常见做法是：

1. 先用 Python 验证玩法和算法；
2. 再把核心逻辑移植/重写为 C；
3. 用 fxSDK/gint 重新适配输入、绘图、时间和资源；
4. 编译为 `.g3a`。

这叫 **port / 移植**，而不是简单的格式转换。

## 6. 重要兼容性提醒

本文以 **fx-CG50** 为实测平台。其他 fx-CG / Prizm 机型可能兼容部分 Add-in 或工具链，但应以具体项目文档为准。

尤其不要用“型号数字更大”推断必然兼容。不同代产品可能有不同 CPU、系统、签名机制或开发工具链。
